## 一、用户确认的产品目标

水源分析终端是**整个投研工程的运行控制台**。用户在同一个仪表盘里查看数据覆盖、启动任务、管理排期、核对本轮结果，并使用已有金融计算和研究能力。后台负责持续采集股票行情、财经资讯、宏观数据与官方财报，按证据状态推进初筛、个股分析、档案、研报和同步。

**简洁约束适用于界面的视觉和信息组织。** 保留总览、事件情报、采集中心、计算分析、系统日志和系统设置六个工作区，以及各自的查询、筛选、详情、任务操作、日志和审计能力。首页突出市场状态、数据缺口、正在运行的任务和常用操作。完整的按钮、排期、历史、参数和底稿在对应工作区按需展开。

**金融计算由后台按业务场景执行，结果作为指标直接展示。** 宏观与市场计算结果放在首页，个股计算结果随选中的公司显示在个股分析中。取消独立计算器的产品形态，已有底层模型继续供后台任务和分析流程调用。个股分析采用左侧选股、右侧详情布局，事件及其他长列表采用分页。

**业务运行包含本地核对同步和数据采集。** 仪表盘的「启动」一次提交两条流程。采集中心分别管理两条流程的任务、排期、运行记录和异常。股票处理以美股和日股的全量资产池为范围，当前核心样本只代表接入阶段。

| 金融计算 | 当前存在自动估值、个股深度分析和独立自定义测算视图。底层已登记多阶段 DCF、WACC、NPV、IRR 和财务比率。 | 将宏观与市场指标接到首页，将个股估值和财务指标并入个股详情，取消独立计算器视图。自动估值目前存在固定或推算的报价、现金流、股数和折现参数回退，也可能在缺平账证据时默认通过。正式结果须使用可核对的事实和显式假设，证据缺失须单独标记。 |

### 总启动和采集中心的两条流程

| 流程 | 职责 | 在采集中心管理的内容 |
| --- | --- | --- |
| 本地核对同步 | 自动检查已有行情、日线、资讯、财报、指标和研究底账，核对版本、时间、完整性和账本。把已验证的数据和成果同步到项目索引、指标结果与仪表盘。 | 单独查看最近核对时间、同步对象、发现的缺口、阻断原因和运行历史，可独立运行、设定排期和重试。 |
| 数据采集 | 从项目允许的来源取得新增行情、日线、宏观数据、财经资讯与官方披露，保存原始证据和归档回执。 | 单独查看各市场和来源的排期、开关、批次进度、成功覆盖、缺口和失败记录，可独立运行和重试。 |

仪表盘「启动」为本轮生成一个运行编号，同时提交两条流程，两条子运行分别记录结果。本地核对可以立即使用已有归档，采集独立取数。新增证据落盘后触发相应范围的增量核对与同步，有数据依赖的计算等待上游校验通过。总览同时展示两条流程的进度，一条流程成功时保留另一条的实际状态。采集中心的独立操作走同一套任务定义与队列。

## 三、界面组织与功能保留

| 工作区 | 主要职责 |
| --- | --- |
| 总览 | 按美股与日股展示市场概况和宏观计算结果，如期限利差、市场宽度与波动指标。显示可验证的证据时间、覆盖和缺口，保留常用任务快捷启动与本轮进度入口。 |
| 事件情报 | 事件雷达和官方来源资讯分别分页。保留筛选、搜索、详情、来源、发布时间、归档和传闻隔离。 |
| 采集中心 | 分设「本地核对同步」和「数据采集」，分别管理排期、手动运行、开关、批次、失败原因和历史。按行情快照、日线、成交量、三表和待补数据核对覆盖。 |
| 计算分析 | 左侧用可搜索、可按市场筛选的选股列表显示代码、公司名与选中状态。右侧展示当前公司的行情状态、财务指标、估值、行业、护城河、供应链、三表和定量诊断。证据与计算底稿按需展开。 |
| 系统日志 | 保留按级别、模块和关键词过滤。运行编号、失败详情、重试和来源回执可用于定位同一次执行。 |
| 系统设置 | 保留环境状态、时效策略、数据存储规则和预测账本验签。状态由实际检查结果驱动。 |

顶栏显示连接和运行摘要，可直达任务详情。总览保留常用动作，采集中心承担完整管理。相同任务在各视图中使用同一运行编号、排期和状态。专业术语、任务编号、证据路径和时间戳在详情中保留，列表用清晰的业务名称。

### 指标与列表交互

- 切换左侧标的时，右侧整组分析随标的更新。结果刷新后保留选中公司、搜索词和市场筛选。窄屏可将选股列表收进抽屉，仍可从详情页直接切换公司。
- 每项计算结果展示数值、单位、适用市场或标的、数据时点和缺口状态。用户可展开查看来源、计算口径及假设；如需调整个股情景参数，在该估值指标内操作。
- 事件雷达、官方资讯、选股列表、采集历史、归档和系统日志等长列表分页。先对完整数据集执行搜索和筛选，再按稳定顺序返回当前页。分页控件显示当前页和可翻页状态；筛选变更回到第一页，打开详情后返回时保留页码与筛选条件。

### 全量计算能力接入

建立从工程公式和引擎到业务场景、触发任务、输入契约与前端指标的覆盖清单。以计算登记表、`financial_core` 的公开引擎与工程指标字典为盘点入口，覆盖宏观、市场、企业财务、现金流、估值、量化、风险和期权等已实现能力。每项能力都须能从其适用场景调用，并在首页、个股详情或对应指标的展开区查看结果、诊断和证据。组合模型所使用的中间公式可在计算底稿中追溯。

公式按输入和适用对象启用。例如市场宽度与宏观传导显示在首页，WACC、DCF、财务比率和信用风险显示在公司详情。REIT、期权等专用模型在适用标的详情显示，缺少输入时显示缺口，不适用的模型不参与该标的计算。整个前端复用后端计算服务，公式和引擎的覆盖以实际调用与可见结果验收。

参考 [金融计算登记](../finance_tools/governance_and_pipeline/service.py) 和 [核心引擎公开入口](../financial_core/engines/__init__.py)。

### 全量股票覆盖

股票索引与左侧选股列表覆盖项目美股 SEC 底账和日股 JPX 底账中的全量标的。按市场、代码或公司名全库检索并分页，缺少行情或财报的标的仍可查询并显示缺口。核心、成长和其他资产分层决定任务优先级和更新频率。采集和初筛按批次覆盖全量底账，分别记录总数、已归档、已筛选、待补、失败与更新时间。全量深度档案管线保留增量能力，正式深研仍遵守真实 OHLCV 初筛准入。

资产池基准取自 [美股 SEC 底账](../data/universe/sec_company_tickers.json) 和 [日股 JPX 底账](../data/universe/jpx_company_tickers.json)。

## 四、正式运行链路

1. 按市场交易日调度行情、宏观、资讯和官方披露。独立任务可以并行，共用底账的写入按资源互斥。手动与定时提交使用同一队列，任务按市场、交易日与分块去重，重启后按已核验检查点续跑。
2. 公共来源和授权 Google Sheets 结果先归档。报价在展示或估值前核验采样时间、时区、交易时段和新鲜度。官方财报经 `OfficialFilingMapper` 清洗，校验资产等于负债加权益。范围之外或缺失的数据进入补数清单。
3. 全市场初筛覆盖 SEC 与 JPX 资产池，分批对约一年日线 OHLCV 执行纯本地 SEPA 计算，初筛阶段零 LLM。只有趋势与形态全票通过后，标的才进入三表、DCF 和深度研报流程。
4. 宏观和市场计算按市场更新首页指标。个股计算在证据充分时自动带入可追溯事实，将结果写入选中公司的分析视图，并显示日期、财报期、币种、单位和估值假设。缺报价时显示待补或经核验的前收盘状态，缺财报或平账证据时停止正式估值。买点以明确的情景触发和风险条件呈现。
5. 按市场生成每日大盘研报，遵守日报与深度档案 Schema。日报和审核通过的档案批次分别触发同步。运行页显示归档范围、时间、失败原因、预测账本签验和真实上传回执。

## 五、当地时间与中文显示规范

**日志和运行状态统一使用用户设备的系统当地时间。** 总览、采集中心、事件列表和系统日志中的提交、开始、完成、更新时间及下次执行时间，共用一套格式化规则。展示日期、时分秒和时区，例如 `2026-11-14 09:42:07（UTC+09:00）`。用户设备切换时区后，同一条记录应按新时区重新显示。按日筛选使用当地日期边界，排序、去重和分页使用原始时间戳。

后台持久化和 API 使用带时区的时间戳，账本与审计保留原始时间。行情详情另外标出交易所当地时间、市场交易日和交易时段。排期按任务配置的时区和市场交易日执行，界面把下次执行时刻换算为用户设备时间。仅有日期或缺失时间时忠实显示来源精度，例如「仅发布日期」或「时间未知」。

**前端面向用户的分级、状态、筛选项、提示和失败原因统一使用中文。** 由共用的状态映射服务于首页、详情、表格筛选、状态标签和通知。接口、账本和日志原文继续保留稳定的机器枚举；详情可展开原码用于排查。未知枚举显示「未知状态」并保留诊断信息。

| 类型 | 前端标签示例 |
| --- | --- |
| 事件分级 | P0「极高」、P1「重要」、P2「动态」、P3「常规」，沿用现有分级含义，标签可附编号 |
| 信源与核验 | 官方来源、已核实、多源佐证、待核验、传闻隔离 |
| 任务执行 | 排队中、运行中、已完成、部分完成、执行失败、已取消、等待前置任务 |
| 数据与行情 | 当日最新、盘前、盘中、盘后、前一交易日收盘价基准、已归档、待补数据、行情超期 |
| 计算与交付 | 可计算、缺少输入、不适用、验签通过、验签失败、待同步、已上传、上传失败 |

任务、数据、计算和交付分别显示状态。例如任务完成后，个别数据仍可待补，云端仍可待同步。正式成功标签由真实归档、计算结果或上传回执驱动。

## 六、代码重构标准

按项目标准重构现有终端的完整调用链，覆盖界面、接口、调度、采集、核对同步、金融计算、状态与数据呈现。开始前列出现有可用功能、调用方、数据写入路径和兼容行为，按工作区与任务逐项验收。历史原型、重复实现和演示入口在替代路径经过验收后再清理。

| 边界 | 代码要求 |
| --- | --- |
| 金融核心与数据治理 | `financial_core/` 保持独立，内部使用相对导入。沿用 `finance_tools/` 的计算门面和校验，`financial_reporting/` 负责证据呈现与行情门禁，`scripts/` 负责调度和批处理。`data/` 经治理入口追加。禁止下层反向依赖上层。 |
| 任务和状态 | 合并重复的执行路径。总启动、单项执行和定时触发复用任务定义、队列、持久化状态和运行编号。本地核对同步与数据采集有各自的子运行。状态迁移、幂等、重试、互斥和断点恢复集中实现。 |
| API 与前端 | 统一请求、响应、错误、分页和推送契约。前端按工作区组织组件，共用中文映射与当地时间格式化逻辑。金融指标由后端计算并返回证据、单位、口径和时效。 |
| 证据与回退 | 将固定报价、模拟初筛结果、伪造估值输入和预置成功状态移出正式路径。财报经 `OfficialFilingMapper` 清洗和平账，缺数据返回可追踪的缺口。外部工具经 `scripts/env_discovery.py` 探测，预测与对账经 `PredictionLedger` 记录和验签。 |
| 兼容和测试 | 验证已有用户操作、归档数据和调用方在重构后仍可用。测试覆盖跨时区和跨日显示、中文映射、分页、全量检索、双流程提交与单路异常、续跑、证据缺失及公式调用。 |

执行依据见 [项目工作约束](../AGENTS.md)。代码改修按顺序通过架构巡检 `python scripts/verify_architecture_integrity.py`、全量测试 `python -m unittest discover -s scripts -p "test_*.py"`、数据治理与知识结构及研究和行业映射四项回归，以及 `ledger.verify_integrity()`。同时验证前端构建和实际业务入口。已有回归失败须定位并处理后再确认交付通过。

## 七、改修验收顺序

1. 隔离样本及无来源回退，核对旧入口和新入口都不会把固定样本、旧摘要或缺失证据显示成正式成功。
2. 点一次「启动」，验证本地核对同步和数据采集均入队，且可在采集中心独立查看、排期、运行和重试。验证单路失败、来源落盘后的增量核对、休市、并发和重启续跑。
3. 按美股和日股底账核对索引总数、搜索分页与各阶段覆盖，验证全量批次及数据缺口。逐项核对计算能力覆盖清单，验证调用、结果展示、证据链接及不适用和待补输入状态。接通官方财报、研报与分批同步并核对实际回执。
