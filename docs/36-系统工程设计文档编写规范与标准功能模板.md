# 系统工程设计文档编写规范与通用功能模板

> **版本**：3.2.0 (朴素语言与降低认知障碍重构版)  
> **核心宗旨**：**文字是看懂代码的说明书**。通过设计文档讲清架构与逻辑、代码内部标清分步与原因、单元测试覆盖正常与踩坑场景，让任何新接手项目的工程师不需要找人反复问，看文档和代码就能直接上手与重构。  
> **适用范围**：适用于全系统所有新建及重构的技术方案、核心业务模块、算法计算引擎、状态流转服务、数据处理管道与服务接口。

## 第一部分：写设计文档的三条硬规矩

写技术文档不是写学术论文，也不是写聊天记录。为了让所有人沟通成本最低，全篇必须遵守以下三条规矩：

### 规矩一：只写拍板后的最终结论，不写讨论过程
1. **直接说系统怎么做**：通篇用陈述句，直接交代清楚“输入是什么、怎么处理、输出是什么”。
2. **禁止写探讨式的问句**：不要在文档里写“如何处理高并发？”、“怎样防止重复下单？”、“是不是该选方案A？”。方案对比属于开会讨论阶段，正式设计文档只写最终拍板的技术实现方案。
3. **说话直接，消除歧义**：按照“谁做某事（主谓宾）”的直白语言写，避免绕弯子和模棱两可的形容词。

### 规矩二：写客观事实，不喊口号、不加感叹号
1. **彻底删掉口语化与口号词**：文档里禁止出现“【必须牢记】”、“【务必小心】”、“【严禁……违者……】”等大模型提示词式的喊话。约束力体现在代码参数校验、抛出明确报错和测试用例上，而不是靠文档里的感叹号。
2. **拒绝生造名词与技术伪包装**：不要把简单的事情故意用高深莫测的生造词汇包装。保持朴素、干净的工程师日常交流文风。
3. **把事实交代清楚**：文档重点讲清楚：**架构长什么样、依赖谁、处理分哪几步、数据格式长什么样、极端情况怎么保底**。

### 规矩三：正常流程写正文，报错拦截放文末清单
1. **正文只专注讲顺畅跑完的业务流程**：从头到尾说明合法入参下一层层怎么流转、数据怎么变换、返回什么正确结果，保证主干逻辑一口气读得顺。
2. **异常与踩坑防护集中放文末清单**：诸如“入参为空怎么拦截”、“除以 0 怎么保护”、“网络超时怎么重试”、“并发防重提交”等负面约束，统一归拢在文末附录的《边界防守与上线自查清单》，不打断正文阅读。

## 第二部分：代码与测试应该怎么写注释？

设计书不是给领导看一眼就束之高阁的摆件，必须能和物理代码、测试用例无缝对应。

### 1. 物理代码怎么写注释？（杜绝废话，讲清原因）

```
┌─────────────────────────┐          ┌─────────────────────────┐          ┌─────────────────────────┐
│      技术设计文档       │ ───────> │      真实业务代码       │ ───────> │      自动化测试集       │
│  (写清输入输出与步骤划分) │ 步骤对齐 │ (函数头引文档 + 步骤标号)│ 针对性测 │ (测算得对 + 测拦得住)   │
└─────────────────────────┘          └─────────────────────────┘          └─────────────────────────┘
```

1. **函数开头指路**：核心类和函数的头部注释里，写一句清楚这个函数干嘛的，并附上对应设计书章节名称，方便查阅。
2. **严禁机械翻译代码（杜绝废话）**：
   - 错误范例：在 `count += 1` 上写 `// 计数器加一`。
   - 正确范例：在代码上写 `// 为什么这里要向下取整保留两位小数：防止分摊出现多扣导致商户资损`。
   - **注释重点解释“为什么这么写(Why)”和“业务背景”，而不是机械复述“代码做了什么(What)”**。
3. **关键处理分步标号（与设计书绝对对齐）**：
   - 代码里的核心段落标出步骤：`# 步骤 1: 参数校验与查重`、`# 步骤 2: 核心阶梯计算`、`# 步骤 3: 结果落盘`。
   - 步骤序号和名称与设计文档第四部分的“分步处理步骤”字面一致，看代码就像在看设计书。
4. **关键入口写清假设**：
   - 在函数入口明确写出关键入参要求（如：金额必须大于 0）。
   - 在函数返回前明确写出返回值要求（如：实结金额不能为负数）。

### 2. 单元测试应该怎么测？（测正常 + 测异常）

测试是验证设计文档和代码有没有漏洞的底线防线，测试代码的注释要让新手一看就懂：

1. **结构化三步走**：每个测试用例内部用三句话注释分隔：
   - `# 准备数据：构造订单金额 1000 元、两档阶梯费率的测试入参`
   - `# 执行调用：调用结算核心引擎`
   - `# 验证结果：检查平台抽成是不是 35 元，商户实得是不是 965 元`
2. **一个踩坑点对应一个测试用例**：
   - 设计书文末清单里列出的每一个防御要求（比如防重复提交、防除以0、防负数金额），测试代码里必须专门写一个测试函数去攻击验证。
   - 测试函数名起直白的大白话英文：比如 `test_settlement_duplicate_request_returns_same_result`（测试重复请求返回相同结果）。
3. **测试注释写清业务场景**：
   - 注释里写明白：“测试当网络抖动客户端连发两次相同请求时，系统必须直接返回第一次的结果，严禁扣两次钱”。

## 第三部分：五大工程分类该重点写什么？

无论什么系统，日常工程代码大致可以分成以下五类。编写设计文档时，对应类别必须包含以下核心内容：

| 类别大标题 | 这个模块本质上是在干嘛（大白话） | 设计文档必须重点交代的内容 |
| :--- | :--- | :--- |
| **类别 A：核心算法与计算引擎** | **纯算账、算指标，不改外部数据**<br>（给它一堆输入，老老实实算出一个结果） | ① 计算公式与业务规则是什么<br>② 第一步算什么、第二步算什么<br>③ 遇到除以 0 或极端大数时怎么保底截断 |
| **类别 B：状态机与工作流引擎** | **管一件事情从头到尾的状态流转**<br>（比如订单从待支付、处理中到已完成） | ① 一共有哪几种业务状态<br>② 发生了什么事件会跳到下一个状态<br>③ 怎么防止同一个请求重复提交两次 |
| **类别 C：数据管道与批流处理 (ETL)** | **批量搬数据、洗数据、跑任务**<br>（从接口或数据库批量拉数据、清洗、落盘） | ① 一次批处理拉多少条数据（防止内存打爆）<br>② 中间字段怎么转换和对齐<br>③ 任务中途报错挂了怎么从断点接着跑 |
| **类别 D：服务接口与网关服务** | **对外提供接口、聚合内部服务**<br>（前端或外部系统调用的统一入口） | ① 接口入参和出参长什么样（标准 JSON 样例）<br>② 调用的下游服务超时了怎么降级兜底<br>③ 接口怎么限流防刷 |
| **类别 E：数据存储与历史账本** | **建数据库表、存流水日志**<br>（决定数据存在哪、怎么查、防篡改） | ① 表结构字段、主键和索引怎么建<br>② 哪些是热数据、历史老数据怎么归档<br>③ 关键业务单据怎么保留变更记录以备对账 |

### 核心示意图简明画法示例

#### 算账流程示意图（类别 A）

                   ├──> [第一步: 基础数据清洗] ──┐
[外部输入参数 B] ──┘                             ├──> [第三步: 核心公式计算] ──> [最终计算结果]
                                                 │
[系统配置参数 C] ─────────> [第二步: 阈值范围检查] ──┘
```

#### 状态流转示意图（类别 B）
```
          [收到新任务请求]
                 │
                 ▼
             [待处理]
                 │
           [执行具体逻辑]
                 │
        ┌────────┴────────┐
     [成功]             [失败]
        │                 │
        ▼                 ▼
   [已成功完成]       [处理失败/已告警]
```

## 七、 代码注释怎么写？（代码与文档对应规范）

在真实业务代码中，必须参照以下格式写注释，方便别人随时看懂：

```python
def process_settlement(req: SettlementRequest) -> SettlementResult:
    """
    计算订单结算金额，并完成结算单状态流转。
    对应文档：[结算模块设计说明书 # 四、具体怎么处理的]
    """
    # 【入参检查】金额必须大于 0，防止负数产生资损
    if req.base_amount <= Decimal("0.00"):
        raise ValueError(f"订单金额非法: {req.base_amount}")

    # 步骤 1: 检查是否重复提交（防重复扣款）
    existing = query_by_idempotency_key(req.idempotency_key)
    if existing:
        return existing.to_result()

    # 步骤 2: 核心阶梯计算（为什么用 Decimal：杜绝浮点数丢失分钱）
    fee = calculate_fee(req.base_amount, req.rates)

    # 步骤 3: 组装结果并落库
    settlement_id = save_settlement(req.order_id, fee)
    return SettlementResult(settlement_id=settlement_id, fee=fee)
```

## 八、 单元测试应该怎么测？（测正常 + 测异常）

测试文件里必须包含以下两类测试：

```python
def test_settlement_normal_input_success():
    """测试在输入正常参数时，能否算出正确的手续费和结算金额"""
    # 1. 准备数据：金额 1000 元，费率 3.5%
    req = make_mock_request(base_amount=Decimal("1000.00"), rate=Decimal("0.035"))

    # 2. 调用方法
    res = process_settlement(req)

    # 3. 验证结果：手续费应为 35 元，净额应为 965 元
    assert res.fee == Decimal("35.00")
    assert res.net_amount == Decimal("965.00")


def test_settlement_duplicate_request_does_not_double_charge():
    """测试重复发送相同请求时，系统直接返回已有结果，严禁重复扣费"""
    # 1. 准备数据并第一次调用成功
    req = make_mock_request(idempotency_key="UNIQUE_KEY_001")
    first_res = process_settlement(req)

    # 2. 模拟网络超时重发，第二次调用相同请求
    second_res = process_settlement(req)

    # 3. 验证返回的是同一笔单号，没有重复计算
    assert first_res.settlement_id == second_res.settlement_id
```

## 附录：边界防守与上线自查清单（防止踩坑的硬性要求）

*(所有可能踩坑的技术细节在此逐条核对，正文保持顺畅清晰)*

- [ ] **参数合法性拦截**：所有必填入参在函数开头做判空和有效区间检查，非法参数直接报错拦截，不往深处传。
- [ ] **金额精度防漏**：涉及钱款和比例计算，全流程强制使用定点数（如 Python `Decimal` / Java `BigDecimal`），禁止使用原生 float 浮点数运算。
- [ ] **防止除以 0**：所有公式里作为分母的变量，计算前必须判断是否大于 0，分母为 0 时有明确的保底逻辑或报错拦截。
- [ ] **防止重复提交**：关键写操作接口必须支持防重键（Idempotency Key），重复请求安全返回历史结果。
- [ ] **超时与重试保护**：调用任何外部服务或数据库操作，必须显式设置超时时间（Timeout），禁止出现无超时永久卡死的情况。
```

## 第五部分：拿来即用的优秀示范样板

### [示范说明书] 交易结算与费率折算引擎技术设计说明书

> **功能代号**：`BILLING_SETTLEMENT_CORE`  
> **所属类型**：类别 B：状态机与工作流引擎  
> **开发状态**：已上线稳定运行  
> **核心代码位置**：`services/billing/settlement_engine.py`  
> **对应测试文件**：`tests/services/billing/test_settlement_engine.py`  

#### 一、 这个功能是干什么的？
本功能负责在电商交易完成后，按照商户签约的阶梯费率，精确计算平台抽成手续费与商户实际应得金额，生成结算流水单并驱动结算单状态流转，为后续财务入账和商户提现提供准确的金额依据。

#### 二、 谁调用我，我调用谁？
1. **上游谁调我**：订单服务在用户确认收货后调用本引擎，传入已完成的订单号和订单总金额。
2. **下游我给谁**：算完后将结算单发给财务账本服务记账，并通过消息通知商户端资金到账。

#### 三、 输入参数说明
| 参数名称 | 字段名 | 数据类型 | 约束条件 | 字段说明 |
| :--- | :--- | :---: | :---: | :--- |
| 订单号 | `order_id` | `String` | 32位唯一字符 | 待结算的订单唯一标识 |
| 订单原始金额 | `base_amount` | `Decimal` | 必须大于 0.00 | 订单总成交金额，精确到分 |
| 阶梯费率列表 | `tier_rates` | `List[Decimal]` | 比例在 0 到 0.3 之间 | 平台在各金额段的抽成比例 |
| 阶梯分段金额 | `tier_thresholds` | `List[Decimal]` | 递增正数 | 阶梯费率的分段截点 |
| 防重请求键 | `idempotency_key` | `String` | UUID 格式 | 防客户端超时重发导致重复结算的令牌 |

#### 四、 具体怎么处理的？

##### 1. 计算规则
阶梯分段累进计费：按分段计算各段手续费相加，手续费分位保留强制**向下截断（ROUND_DOWN）**，确保商户端不发生多扣资损。
- 平台手续费总额 = 各分段金额 $\times$ 分段费率 之和
- 商户应得净额 = 订单原始金额 - 平台手续费总额

##### 2. 分步处理步骤
1. **步骤 1：防重拦截与入参校验**  
   先根据 `idempotency_key` 查历史记录。如果之前已经算过这笔单子，直接返回上次结算成功的单据；同时检查金额必须大于 0。
2. **步骤 2：阶梯费率分段计算**  
   根据阶梯断点逐段扣除计算手续费，全程使用 `Decimal` 定点计算，避免分钱上的精度漂移。
3. **步骤 3：数据落盘与状态流转**  
   在数据库事务中保存结算单明细，将状态标记为“结算完成”，发送异步通知事件。

#### 五、 状态是怎么流转的？
```
[接收结算请求] ──> [检查防重令牌] ──> [执行分段计算] ──> [落盘入库] ──> [状态: 已结算完成]
                          │ (发现已结算过)
                          └───────────────────────> [直接返回历史单据]
```

#### 六、 物理代码实现真实范例
在 `services/billing/settlement_engine.py` 中的代码实现：

```python
from decimal import Decimal, ROUND_DOWN
from typing import List

class SettlementEngine:
    """
    订单阶梯费率结算核心引擎。
    对应文档：[BILLING_SETTLEMENT_CORE # 四、具体怎么处理的]
    """

    def process_settlement(self, req: SettlementRequest) -> SettlementResult:
        # 【入参检查】金额必须大于零，防止负数产生资损
        if req.base_amount <= Decimal("0.00"):
            raise ValueError(f"订单金额必须大于0，当前值: {req.base_amount}")

        # 步骤 1: 检查防重键，防止重复提交造成多次结算
        existing = self.db.find_by_idempotency_key(req.idempotency_key)
        if existing:
            return existing.to_result()

        # 步骤 2: 阶梯费率分段计算（为什么用 Decimal：杜绝浮点数计算失真）
        total_fee = Decimal("0.00")
        last_threshold = Decimal("0.00")

        for rate, threshold in zip(req.tier_rates, req.tier_thresholds):
            if req.base_amount > threshold:
                segment_amount = threshold - last_threshold
                total_fee += segment_amount * rate
                last_threshold = threshold
            else:
                remaining_amount = req.base_amount - last_threshold
                total_fee += remaining_amount * rate
                break

        # 【舍入保底】手续费向下保留两位小数，确保商户端不发生多扣
        final_fee = total_fee.quantize(Decimal("0.01"), rounding=ROUND_DOWN)
        merchant_net = req.base_amount - final_fee

        # 步骤 3: 存库落盘并标记成功状态
        settlement_id = self.db.save_settlement(
            order_id=req.order_id,
            fee=final_fee,
            net_amount=merchant_net,
            status="SUCCESS"
        )

        return SettlementResult(
            settlement_id=settlement_id,
            order_id=req.order_id,
            fee=final_fee,
            merchant_net=merchant_net,
            status="SUCCESS"
        )
```
