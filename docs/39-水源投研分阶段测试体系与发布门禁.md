# 水源投研分阶段测试体系与发布门禁

本体系把四类测试和业务交付阶段结合起来。四类回答“在哪一层发现问题”，五个阶段回答“输入到交付的哪一段已经验证”。[四类测试点清单](38-水源投研工程四类测试点与验收清单.md)保留测试点编号，[设计场景矩阵](../scripts/test_support/release_plan.json)记录设计书、业务场景、对应探针和验收证据。

## 分阶段运行

| 顺序 | 阶段 | 先核验的合同和副作用 |
| --- | --- | --- |
| 01 | `inputs` 证据接入与行情门禁 | 冻结交易日和时区，校验有效与非法报价、逐卡时效、来源回执、原文字节摘要、六步研究和引用边界 |
| 02 | `models` 财务归一与模型计算 | 用闭式公式、等值变换和固定种子校验平账、单位、DCF、隐波、期权树、ETF、黄金与 SEPA 输入边界 |
| 03 | `state` 状态、账本与恢复 | 用隔离 SQLite 和任务状态回放幂等、并发、损坏账本、跨市场同代码、缺失产物恢复和扩展准入 |
| 04 | `reports` 研报和存量产物 | 读取实际美日五页工作簿，校验 Schema、证据字段、HTML 转义、图谱与评级约束，并回扫存量档案 |
| 05 | `delivery` 调度、交付与部署 | 核验定时参数、日报发布阻断、PDF 新旧产物、逐件交付顺序和本次收据。真实部署另取证 |

```powershell
python -X utf8 scripts/audit_project_contracts.py --matrix
python -X utf8 scripts/audit_project_contracts.py --stage inputs
python -X utf8 scripts/audit_project_contracts.py --stage models --stage state
python -X utf8 scripts/audit_project_contracts.py --spec SPEC-06 --spec SPEC-08
python -X utf8 scripts/audit_project_contracts.py --stage all --json
```

阶段按固定顺序执行，共用探针只运行一次。运行输出区分 `PASS`、`FAIL` 和 `ERROR`。阶段输出中的 `PENDING` 表示场景尚无直接自动化证据，也会使该阶段返回非零。场景的 `PASS` 仅汇总所列探针，不扩展到未测分支。`--matrix` 用于查看登记情况，其退出码不代表实际验收。直接复现单条缺陷可继续用 `--check`、`--point` 或 `--layer`。

## 怎样判断覆盖充分

每次改动先从被改的正式入口回溯到设计要求和上下游。每项要求按适用情况逐项登记以下证据，避免用一个成功样例替代整个功能。

| 维度 | 必须留下的证据 |
| --- | --- |
| 正常与独立基准 | 验证可复算数值、正确状态和实际文件内容。两份等值单位的财报应得到同一每股结果 |
| 错误与边界 | 对缺项、非有限数、前收盘、过期、非法路径、超时、坏回执断言具体拒绝原因及无正式副作用 |
| 重试与并发 | 在写入前、写入后和收据提交前分别中断。复跑比对任务、文件和账本。真实多进程互斥单独取证 |
| 产物与存量 | 结构合格和可发布分别统计。实读 JSON、XLSX、SQLite，部署环境补实际 PDF 和远端回读哈希 |
| 数据与环境组合 | US/JP、股/ETF/黄金、币种和量纲分别抽样。时间敏感入口覆盖节假日、提前收盘、DST 和时区换日 |
| 变更防回归 | 增删设计场景时同步更新矩阵。登记测试会拒绝未分配探针、重复场景、无效设计路径和未知探针编号 |

## 发布前的顺序

1. **准备**。记录版本、交易日历版本、时区、固定夹具与哈希、状态基线。写入全部走临时目录。先用一个正常和一个拒绝用例确认测试夹具自身可用。
2. **项目硬门禁**。按工程约定执行架构完整性、全量单测、四项治理回归和正式预测账本副本验签，分别保留退出码和失败原因。用例数只增不减。
3. **分阶段审计**。按上表跑到交付阶段。修复后先重跑失败探针，再复跑所在阶段和下游阶段。阶段内任何失败、环境错误或待验收项必须在发布记录中单列。
4. **环境验收**。实际交易日历、跨进程锁和长批性能、真实浏览器原文、首期资格到横向扩展、Actions 续跑、PDF 视觉与 Drive 回读都需要专用环境或真实已归档夹具。模拟上传成功只能证明控制流。实际交付以运行 ID、远端文件 ID、可读文件及摘要、账本链头和恢复收据为证。
5. **签收**。记录每项设计场景对应的探针结果及尚未覆盖的分支。测试报告至少保存执行版本、运行环境、阶段、场景编号、实际值、预期值、报告/账本副作用和证据路径。失败、环境阻塞和缺证据分别统计。

当前矩阵从项目关键设计书选取发布风险高的场景。宏观、信用与制度联动、完整波动率曲面、行业绑定组合、千家压力与真实部署仍有待补证据。清单关联率、用例通过率和发布签收应分别核算。

## 新旧设计书口径

矩阵保留原始设计章节的路径，并提供 `SPEC-01` 至 `SPEC-12` 的映射。使用 `--spec` 可以按新设计书回归其关联场景，重复引用的探针只执行一次。关联证明已建立追溯关系，具体测试边界仍看场景和取证字段。

- **调度时间**。现有项目约束要求 JST 07:00 和 16:00，`SPEC-11` 仍写 UTC 21:30 和 07:30。当前探针继续按项目约束核验，矩阵保留待确认的设计口径。
- **账本验签**。`SPEC-12` 示例把验签结果直接作为布尔值使用。当前结果对象是非空元组，失败也可能被当作真。发布验签取 `is_valid`，另有坏账本探针验证失败分支，文档示例待统一。
- **工作簿入口与口径**。`SPEC-01` 和 `SPEC-02` 指定的工作簿脚本在当前仓库缺失。现有美日档案回读探针执行公司深度档案建造器，覆盖该建造器的实际五页和证据字段。新规格的资产池工作簿仍需确认入口及页签合同。
