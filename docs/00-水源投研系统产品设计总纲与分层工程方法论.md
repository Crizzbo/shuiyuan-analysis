# 水源投研系统产品设计总纲与分层工程方法论 (System Architecture & Product Methodology)

> 版本：1.0.0  
> 编写基准：吸纳现代企业级软件工程最佳实践与买方投研机构落地经验，确立“单一事实来源（SSOT）”、“三层职责物理隔离”与“严格单向变更管理”。

---

## 一、 系统顶层定位与设计哲学

水源分析系统（Shuiyuan Analysis）定位为**买方机构级智能投研与资产配置系统**。系统服务于专业投资机构的投委会研判、宏观微观传导归因、财报法证穿透与精准买点择时。

在产品设计与工程实现层面，全系统必须坚决贯彻以下四大哲学底线：

1. **单一事实来源（SSOT）与拒绝两张皮**：
   - 所有的财务指标、估值防线、状态评级与操盘指令，必须在整个链条中拥有唯一且明确的权威来源；
   - 严禁在多处代码、文档或前端写死重复或相互矛盾的魔法数值、比例或计算逻辑。
2. **纯动态数据驱动与杜绝虚假模板文本**：
   - 所有的报表、工作簿、卡片与纪要，必须由物理归档的真实数据或金融引擎动态算出；
   - 若某项数据尚未披露或分析师暂未录入，必须显式标注“待录入 / 待 AI 分析”，严禁自动捏造数字或使用假模板敷衍。
3. **去工程符号化，贴近商业与投资直觉**：
   - 面向用户的 UI 标签、研报卡片、Excel 工作表及投委会决策备忘录中，**严禁暴露纯工程符号与代码代号**（如 `L1/L2`、`stage_2`、`p_floor`、`wsState` 等）；
   - 必须统一转换为自然中文的商业语义与投资动作指令（如“第二阶段主升浪”、“悲观紧缩防御底”、“放量突破果断开火”）。
4. **先打样，再批量 (Sampling POC First)**：
   - 在执行大规模重构、全资产池千家批量渲染或复杂模型迭代前，必须先完成 1 家核心标的（如 NVDA）的全息样板实测并验证闭环；
   - 效果确认无误后，再全量批量铺开，杜绝方向性偏差带来大规模返工。

## 二、 产出物分层体系与职责边界 (Layered Artifacts Architecture)

为防止系统开发过程中“文档打架、字段混乱、逻辑割裂”，水源投研系统严格实施**产出物五层单向流转架构**：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 1. 业务上下文与需求调研 (Business Requirements & Scenarios)                    │
│    文件：docs/00a-*.md, docs/01-*.md                                        │
│    职责：厘清买方场景、角色动线、核心痛点、一期核心主动脉与二期明确排除清单    │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ 单向传导
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 2. 字段事实清单 (Field Schema TSV / JSON Schema)                              │
│    文件：schemas/*.json, docs/*-dictionary/*.md                             │
│    职责：【字段唯一事实源】严格定义字段名、数据类型、精度、枚举值、必填条件与约束│
│    铁律：严禁在此层定义界面排版与交互表现，它是纯粹的数据契约                 │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ 单向传导
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 3. 业务规则与模型 PRD (Business Logic & Engine Specification)                 │
│    文件：docs/09-*.md, docs/21-*.md, docs/33-*.md                           │
│    职责：【逻辑唯一事实源】状态机流转、阻断门禁、数学公式、状态-功能操作矩阵  │
│    铁律：不堆砌组件参数，不自创新字段，专注金融数学与业务因果               │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ 单向传导
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 4. 报告呈现与交互 PRD (Presentation & Delivery Specification)                │
│    文件：financial_reporting/, docs/19-*.md, docs/27-*.md                   │
│    职责：【呈现唯一事实源】多模态载体映射 (HTML/Markdown/Excel/PDF)、控件选型│
│    铁律：严禁在呈现层私自发明状态、隐藏按钮或增加未定义的业务字段             │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ 单向传导
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 5. 代码实现与自动化回归门禁 (Implementation & Immutable Verification)         │
│    文件：financial_core/, scripts/test_*.py                                 │
│    职责：实现纯净解耦代码，并通过四大硬核验收门禁（AST扫描/单测/治理/账本验签│
└─────────────────────────────────────────────────────────────────────────────┘
```

### 产出物分工与责任对照表：

| 产出物层级 | 核心承载内容 | 权威职责定位 | 严格禁止与避免事项 |
| :--- | :--- | :--- | :--- |
| **业务上下文与调研** | 投委会角色、买方场景动线、痛点矩阵、阶段范围 | 业务意图基准 | 避免混入具体 SQL 字段定义或底层算法伪代码 |
| **字段事实清单** | 字段名、数据类型、精度、来源、默认值、必填性 | **字段事实唯一源** | 严禁定义排版样式、前端颜色或组件交互属性 |
| **业务规则 PRD** | 状态机定义、状态-功能矩阵、数学边界、阻断条件 | **业务逻辑唯一源** | 严禁复写全量字段定义副本，不堆砌 UI 布局参数 |
| **呈现与交互规范** | 颜色 Token、表格排版、徽章样式、报错显示位置 | **呈现表现唯一源** | **严禁在页面层自创状态、算法指标或新增未登记字段** |
| **代码与测试套件** | Python 纯净计算引擎、报告渲染器、回归测试用例 | 系统运行实体 | 严禁包含未经 PRD 确认的“私货逻辑”或假数据 Mock |

## 三、 约束分层规范 (Three-Tier Constraints)

在系统设计中，针对任何一个数据项或指标，必须清晰归属于以下三层约束之一，杜绝层次混淆：

1. **第一层：字段事实级约束 (Field-Level Facts)**
   - 规定字段本身的固有物理属性。
   - 例如：`val_pivot_price` 必须为浮点数、单位为美元/日元、精度为美分（保留 2 位小数）、数值必须大于 0.00。
2. **第二层：业务规则级约束 (Business-Level Rules)**
   - 规定跨字段、跨单据或跨状态的金融业务强校验。
   - 例如：
     - 若 `val_current_price > val_extended_limit_price`，必须触发 `EXTENDED_OVERBOUGHT` 超买拦截，系统操作指令强制为“严禁追高”；
     - 资产负债表必须刚性满足 $Assets = Liabilities + Equity$，否则阻断建档；
     - 股价未在 200 日线上方且 200 日线未向上抬升时，一票否决第二阶段主升浪判定。
3. **第三层：页面呈现级约束 (Presentation-Level Constraints)**
   - 规定面向终端用户的视觉色彩、排版规则与高亮反馈。
   - 例如：
     - 当买入信号触发时，状态徽章背景色设为墨绿色（`#2f855a`）；
     - Excel 工作簿中枢轴买点行采用浅绿底纹（`COLOR_BUY_ZONE_GREEN`）与深绿加粗文字；
     - 超买拦截行采用警戒橙底纹（`COLOR_WARNING_ORANGE`）。

## 四、 变更管理标准流程 (Change Management SOP)

任何需求变动、算法优化或字段增减，**严禁“自底向上”或“在表现层打补丁”**。必须严格遵循单向变更传导链路：

```
[步骤 1: 判定变更类型]
  ├─ 字段增减/改名 ────> 先改【字段事实清单 / JSON Schema】
  ├─ 逻辑/算法/规则 ───> 先改【业务规则 PRD】与【状态空间注册表】
  └─ 仅样式/排版微调 ──> 仅改【呈现与交互 PRD】
           │
[步骤 2: 顺向级联更新]
  └─ 从上游源头向下一层逐级更新，同步关联说明书
           │
[步骤 3: 逆向交叉核验]
  ├─ 检查下游文件是否引用了已被废弃的旧字段
  └─ 确保呈现层未暴露未在 PRD 注册的状态
           │
[步骤 4: 代码实现与回归门禁]
  ├─ 运行 AST 语法树无逆向依赖扫描 (`verify_architecture_integrity.py`)
  ├─ 执行全量单元测试与治理回归 (`python -m unittest discover`)
  └─ 验证不可篡改预测账本验签 (`verify_integrity()`)
```

## 五、 交付前双向十字走查清单 (Pre-Delivery Verification Checklist)

在任何产品功能、研报流水线或算法引擎发布前，产品经理与核心架构师必须逐项核对并勾选以下自检项：

- [ ] **字段收敛性检查**：报表与前端展示的所有字段，是否 100% 收敛于《字段事实清单》？是否存在未登记的“野生字段”？
- [ ] **状态完整性检查**：所有的业务状态是否已在 `METRICS_STATE_REGISTRY` 中强类型登记？是否有对应的商业直觉与应对指令？
- [ ] **逆向与容灾走查**：
  - 遇到黑天鹅暴跌、深度洗盘（深蹲）或数据源缺失时，系统是直接崩溃报错，还是安全降级并触发保护？
  - 是否存在除零、负价格或负库存等穿透漏洞？
- [ ] **去工程符号化检查**：所有面向用户的卡片、Excel 单元格和研报中，是否已彻底消除了下划线变量、枚举键名及抽象代号？
- [ ] **四大门禁验收全绿**：架构巡检 0 违规、单元测试 100% PASS、治理回归全绿、预测账本哈希不可篡改。
