## 一、 功能背景与业务用途

### 1. 业务背景
在买方机构研究与量化回测的工程闭环中，“前瞻性信息偏差”（Look-ahead Bias）是导致策略在实盘中严重失效的最隐蔽元凶。传统投研数据库在处理证据时间时面临两大核心痛点：一是财报现实与契约要求的错配——官方财报原件（如 SEC 10-K 或公司公告）通常仅标注披露日期（如 2026-03-15），缺乏精确到秒的上传时刻，早期契约（v1.0.0）强制填写精确时刻（`published_at`），导致分析师或采集程序被迫凭空“脑补/捏造”虚假的发布分钟与秒数；二是将发布时间与公众可得时间混淆，忽略了监管披露到终端实际可合法获取之间的时滞。为此，本项目设计并上线了研究与资料契约 v1.1.0，引入三级发布时间精度体系，构建严格的单向因果时间防线及平滑无损迁移工具。

### 2. 核心用途
本功能解决全系统三大时空证据治理与历史迁移问题：
1. **多精度发布时间模型 (Publication Precision)**：显式支持 `instant`（已知带时区精确时刻）、`date`（仅有官方日期）与 `unknown`（完全未知），诚实记录披露凭据，杜绝伪造时间戳；
2. **刚性单向时间偏序因果断言**：在任何精度下均严格核验 $t_{\text{published}} \le t_{\text{available}} \le t_{\text{as\_of}} \le t_{\text{recorded}}$，并基于 UTC+14 全球最早日界排除未来日期穿越；
3. **1.0.0 ➔ 1.1.0 无损迁移与级联重验**：通过 `migrate_research_time_contract.py` 实现历史快照无损升级，自动递增修订号（`revision`），并将已开展步骤标记为 `invalidated` 触发重新复核，杜绝旧结论带病运行。

## 二、 系统架构上下文与依赖关系

### 1. 前置依赖 (Inputs From Upstream)
- `data/catalog/`：提供 SHA-256 内容寻址不可变存储的原始财报底稿。
- `schemas/source-manifest.schema.json` (v1.1.0)：提供包含发布精度的来源登记凭证。

### 2. 后置消费 (Outputs To Downstream)
- `scripts/validate_research.py`：消费多精度时间戳，执行时间偏序拓扑检验。
- `scripts/data_store.py` (`DataStore`)：只追加封存通过时间契约检验的不可变研究快照。
- `financial_core/`：消费严格锁定时效的财务事实驱动量化回溯。

### 3. 数据流转时序图
```
┌──────────────────────────────────────┐
│  原始财报登记 (可能仅有披露日期)     │
└──────────────────┬───────────────────┘
                   │ (提取精度: instant / date / unknown)
                   ▼
┌──────────────────────────────────────┐
│  时间契约门禁核验器 (validate_research)│
│  ├── 精度与字段并存断言 (三键齐全)   │
│  ├── 单向时间偏序 (published <= avail)│
│  └── UTC+14 最早日界排除未来穿越     │

                   │ (时间因果核验 100% PASS)

│  (生成带 revision 的不可变 .json 快照)│
└──────────────────────────────────────┘
```

## 三、 输入参数契约说明 (Input Contracts)

时间契约三级精度与时间字段配置规范如下表：

| 精度枚举 (`publication_precision`) | 精确时刻 (`published_at`) | 披露日期 (`published_date`) | 公众可得时点 (`available_at`) | 业务含义与约束规则 |
| :--- | :--- | :--- | :--- | :--- |
| `instant` | `YYYY-MM-DDThh:mm:ssZ` | `YYYY-MM-DD` (可选/匹配)| `YYYY-MM-DDThh:mm:ssZ` | 官方提供了经核验的带时区精确发布时刻，日期必须与其在原时区内完全一致。 |
| `date` | `null` (刚性为 null) | `YYYY-MM-DD` | `YYYY-MM-DDThh:mm:ssZ` | 仅有官方披露日期；严禁反推时刻；`available_at` 填首次被本项目观测到可得时刻。 |
| `unknown` | `null` (刚性为 null) | `null` (刚性为 null) | `YYYY-MM-DDThh:mm:ssZ` | 披露时间完全未知；但仍必须有明确的可得时刻以锁定前视界限。 |

### 2. 核心数学模型推导

1. **单向时间因果拓扑偏序严格不等式**：
   $$\text{Epoch}(t_{\text{published}}) \le \text{Epoch}(t_{\text{available}}) \le \text{Epoch}(t_{\text{as\_of}}) \le \text{Epoch}(t_{\text{recorded}})$$
   $$\text{Epoch}(t_{\text{available}}) \le \text{Epoch}(t_{\text{acquired}}) \le \text{Epoch}(t_{\text{recorded}})$$
   若任意偏序关系倒挂，直接抛出 `TimeContractViolationError` 阻断。
2. **全球最早日界未来穿越排除不等式 (UTC+14 Boundary Check)**：
   针对仅有日期而无时区的 `published_date`，取 UTC+14 时区判定全球自然日起始点：
   $$\text{Epoch}_{\text{earliest}}(D_{\text{pub}}) = \text{DateToEpoch}(D_{\text{pub}}, \text{tz}=+14:00)$$
   $$\text{Epoch}_{\text{earliest}}(D_{\text{pub}}) \le \text{Epoch}(t_{\text{available}})$$
3. **无损修订连续性单调递增约束**：
   $$\text{Revision}_{k+1} = \text{Revision}_k + 1, \quad \text{Hash}(\text{Record}_{k+1}) \neq \text{Hash}(\text{Record}_k)$$

## 附录：工程实现与边界自查清单 (Engineering Defense Checklist)

- [ ] **严禁伪造不存在的精确发布时刻**：对仅有披露日期的官方财报，必须标记 `publication_precision: "date"` 并将 `published_at` 置为 `null`，严禁代码凭空填充时刻。
- [ ] **时间契约三键必须同时显式出现**：在 1.1.0 契约下，`publication_precision`、`published_at` 与 `published_date` 三键必须同时出现，严禁遗漏任何一个键。
- [ ] **单向因果偏序刚性断言**：必须满足 $t_{\text{published}} \le t_{\text{available}} \le t_{\text{as\_of}} \le t_{\text{recorded}}$，若发生前瞻穿越必须立即抛出异常拒绝入库。
- [ ] **严禁直接覆盖历史不可变快照**：迁移升级必须递增 `revision` 并生成新文件，严禁物理覆盖已入库封存的 1.0.0 历史研究快照。
- [ ] **迁移步骤必须级联重置失效**：运行迁移工具时，所有已开展的工序必须重置为 `INVALIDATED` 状态并强制要求重新复核，杜绝旧结论未审核流通。
